# Практическая работа
## Тема: Автоматизация CI/CD для облачных веб-приложений

**Проект:** CryptoFlow — демонстрационный криптокошелёк  
**Инструменты:** GitHub, GitHub Actions, GitHub Pages, Visual Studio Code, HTML, CSS, JavaScript.

## Часть 1. Теоретическая

**1. Что такое CI/CD и для чего используется данная технология?**  
CI/CD — набор практик автоматизации разработки и выпуска программного обеспечения. Он помогает быстрее проверять изменения, находить ошибки и доставлять обновления пользователям.

**2. В чём разница между Continuous Integration, Continuous Delivery и Continuous Deployment?**  
- Continuous Integration (непрерывная интеграция) — разработчики регулярно объединяют код, после чего автоматически запускаются проверки и тесты.
- Continuous Delivery (непрерывная доставка) — проверенная версия автоматически подготавливается к выпуску, но публикация может требовать ручного подтверждения.
- Continuous Deployment (непрерывное развёртывание) — каждое изменение, успешно прошедшее проверки, автоматически публикуется в рабочей среде.

**3. Что такое CI/CD Pipeline?**  
Это последовательность автоматизированных этапов: получение исходного кода, сборка, проверки, тестирование и публикация приложения.

**4. Для чего используется GitHub Actions?**  
GitHub Actions — инструмент автоматизации внутри GitHub. С его помощью можно запускать тесты, проверки, сборку и публикацию проекта при определённых событиях.

**5. Что такое Workflow и какова его роль?**  
Workflow — сценарий автоматизации, описанный в YAML-файле. Он определяет событие запуска, задания, шаги и условия их выполнения.

**6. Что такое YAML и почему он используется для настройки автоматизации?**  
YAML — текстовый формат представления структурированных данных. Он легко читается человеком и используется для описания настроек Workflow.

**7. Какие преимущества автоматического тестирования?**  
Оно быстрее находит ошибки, уменьшает количество ручной работы, помогает не допускать повторного появления старых ошибок и повышает стабильность проекта.

**8. Какие риски могут возникнуть при неправильной настройке CI/CD?**  
Можно случайно опубликовать нерабочую версию, раскрыть секретные ключи, предоставить лишние права, использовать уязвимые зависимости или настроить неправильную ветку публикации.

### Схема CI/CD Pipeline

```text
Разработчик изменяет код
          |
          v
     git push в main
          |
          v
  GitHub Actions запускает Workflow
          |
          v
    Получение исходного кода
          |
          v
  Проверка файлов и JavaScript
          |
       Успешно?
       /     \
     Нет      Да
      |        |
  Ошибка в     v
  Actions   Загрузка сайта
               |
               v
        Публикация GitHub Pages
               |
               v
        Сайт доступен в интернете
```

**Объяснение этапов:**
1. Разработчик изменяет файлы сайта.
2. Команда `git push` отправляет изменения в репозиторий GitHub.
3. GitHub Actions обнаруживает push в ветку `main` и запускает Workflow.
4. `actions/checkout` получает исходный код.
5. Проверяются наличие обязательных файлов, синтаксис JavaScript и ссылки на CSS/JS.
6. Если проверка не пройдена, публикация не запускается.
7. Если проверка успешна, GitHub Pages получает файлы проекта и публикует сайт.

## Часть 2. Практическая

Создан сайт CryptoFlow — учебный интерфейс криптокошелька. В нём есть обзор баланса, список криптовалют, конвертер, демонстрационный обмен, история операций и переключение темы.

Автоматизация находится в `.github/workflows/deploy.yml`. Workflow запускается при отправке изменений в `main` или вручную через `workflow_dispatch`.

В Workflow два задания:
- `validate` — получает код и проверяет наличие файлов, синтаксис JavaScript и подключения CSS/JS.
- `deploy` — запускается только после успешной проверки (`needs: validate`) и публикует файлы через GitHub Pages.

Для публикации заданы разрешения `contents: read`, `pages: write`, `id-token: write`.

## Часть 3. Аналитическое задание

**1. Разработчик отправил на GitHub код с ошибкой. Как CI/CD Pipeline должен отреагировать?**  
Pipeline должен запустить проверки. Если ошибка обнаружена, проверка завершается неудачно, GitHub показывает ошибочный статус, а публикация не выполняется.

**2. Что произойдёт, если этап тестирования завершится неудачно?**  
Следующие зависимые этапы не запустятся. Разработчик увидит ошибку в Actions, исправит код и отправит изменения повторно.

**3. Почему автоматическое развёртывание сокращает время разработки?**  
Не нужно вручную копировать файлы и повторять одинаковые действия после каждого изменения. Публикация запускается автоматически.

**4. Какие последствия могут возникнуть, если опубликовать приложение без предварительной проверки?**  
Пользователи могут получить сайт с ошибками, неработающими функциями, уязвимостями или потерей данных.

**5. Почему CI/CD особенно полезен при командной разработке?**  
Все изменения проходят единые автоматические проверки. Это помогает раньше замечать конфликты и ошибки, поддерживать одинаковый процесс выпуска и быстрее совместно работать над проектом.

## Часть 4. Контрольные вопросы

**1. Как расшифровывается CI/CD?**  
Continuous Integration / Continuous Delivery или Continuous Deployment — непрерывная интеграция / непрерывная доставка или развёртывание.

**2. Чем отличается ручная публикация от автоматической?**  
При ручной публикации человек самостоятельно выполняет шаги выпуска. При автоматической публикации их выполняет настроенный Pipeline.

**3. Для чего нужен файл deploy.yml?**  
Он описывает автоматический процесс проверки и публикации сайта.

**4. В какой папке GitHub хранятся Workflow?**  
В папке `.github/workflows` в корне репозитория.

**5. Какую функцию выполняет команда push?**  
Отправляет локальные коммиты в удалённый репозиторий.

**6. Что такое GitHub Pages?**  
Сервис GitHub для публикации статических сайтов из репозитория.

**7. Как проверить успешность выполнения Pipeline?**  
Открыть вкладку Actions и проверить, что Workflow и все задания завершились успешно (зелёная галочка).

**8. Можно ли использовать CI/CD для крупных облачных приложений?**  
Да. CI/CD применяется в крупных проектах и может автоматизировать тестирование, сборку, развёртывание и мониторинг. Для этого добавляют дополнительные проверки, среды и меры безопасности.

## Результаты и материалы для сдачи

- GitHub-репозиторий: добавить ссылку после загрузки проекта.
- Опубликованный сайт: добавить ссылку после успешного запуска GitHub Pages.
- Файл конфигурации: `.github/workflows/deploy.yml`.
- Скриншот успешного Workflow: сделать во вкладке Actions после публикации.
- Скриншот обновлённого сайта: изменить текст, выполнить `git push`, дождаться Workflow и сделать скриншот.

**Вывод:** в ходе работы создан демонстрационный веб-сайт и настроен CI/CD Pipeline. При отправке изменений GitHub Actions автоматически проверяет проект и, если проверки успешны, публикует его через GitHub Pages.
